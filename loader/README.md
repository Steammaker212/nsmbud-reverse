# Loader: from decompiled C to a runnable mod

This directory turns the decompilation into a patch. It gives a hook author the
three things a mod needs: **where** to branch, **what the symbol is called**, and
**what the function actually does** — all three generated from one measured
source, so they cannot disagree.

## What is generated vs. what is vendored

Generated by us, from the binary (`scripts/pipeline/`):

| File | Contents |
| --- | --- |
| `data/loader/main.sym` | 9,671 named symbols as `name = 0xRVA;`, every RVA checked to fall inside a real section |
| `data/loader/symbols.csv` | the same with size, raw name and the corpus file to read |
| `data/loader/stub_maplist.txt` | 1,789 `operator_delete` veneers, all branching to one address |
| `hooks/hooks.hks` | 60 hook sites, each found by decoding a real `B`/`BL` and verifying its displacement |
| `hooks/hooks.json` | the same with the target name, size and caller count |

Vendored from [codedx](https://github.com/RicBent/codedx) (**GPL-3.0**, see
`LICENSE` in this directory):

| File | Why |
| --- | --- |
| `linker.ld`, `sdk.ld` | module layout for a Switch NSO |
| `source/crt0.s` | module entry and MOD0 header |
| `scripts/*.py` | `elf2nso`, IPS generation, hook parsing |

**Licensing:** the vendored files are GPL-3.0 and that licence applies to them.
The analysis output under `data/`, `decompiled/` and `hooks/` is our own finding
from the retail binary and is not derived from codedx code.

## The pieces line up

One fact drives everything: the RVA of a named function. The pipeline writes it
once, in `data/loader/main.sym`, and the linker script, the `.hks` hooks, and the
corpus file names all reference that same number.

```
main.i64 ──► db_state.json ──► emit_symbol_map.py ──► main.sym ──► linker
                    │                                    │
                    └──► gen_hooks.py ───────────────────┴──► hooks.hks
```

`symbols.csv` carries `corpus_file`, so from a hook you can open the exact C that
describes the function you are branching over.

## A hook, end to end

`hooks/hooks.hks` is the format codedx's `hooks_to_ips.py` consumes:

```
ActorMgr__create_hook:
    type:   blal
    func:   ActorMgr__create_hook
    addr:   0x00005664
    # -> ActorMgr__create (0x0021F2A4), 323 caller(s)
```

- `type` is the branch kind decoded from the instruction actually at that site.
- `addr` is the RVA of that instruction.
- `func` is the C function you must provide; its address is resolved from
  `main.sym`.

To add a hook, take a row from `symbols.csv`, find a `B`/`BL` that targets it
(`hooks.json` already lists verified ones), and write the replacement in
`loader/hooks/`.

## Build

```sh
# 1. regenerate the map and hooks from the database export
python scripts/pipeline/emit_symbol_map.py --state <db_state.json> \
    --elf convertedmain.rebased.elf --out data/loader
python scripts/pipeline/gen_hooks.py --elf convertedmain.rebased.elf \
    --symbols data/loader/symbols.csv --out hooks

# 2. assemble and link the module (needs devkitA64 / aarch64-none-elf gcc)
make -C loader

# 3. turn the ELF into hooks + an NSO patch
python loader/scripts/hooks_to_ips.py hooks/hooks.hks loader/out/mod.elf
```

## Verified, not assumed

Every hook site in `hooks.hks` was produced by decoding the instruction word,
computing the branch displacement, and confirming it lands on the intended
symbol. `scripts/pipeline/verify_hooks.py` re-checks all of them independently
and is run before anything is committed.
