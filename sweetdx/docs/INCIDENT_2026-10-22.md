# Incident 2026-10-22 — rendering corruption and crash on Hammer pickup

Reported after installing the SweetDX build into a real console:

1. **Significant rendering issues** in the level, before any Hammer was touched.
2. **Crash on touching the Hammer** question-block item.

Two independent causes. Both were confirmed by reading the retail binary, not inferred.

---

## Cause 1 — the six "table redirect" hooks wrote code pointers into live lookups

`hooks/mode_tables.hks` contained six hooks described as *"redirect to the relocated
body-type / height / draw-offset table"*. They were labelled `type: instr`, but the
words they write are **not instructions**.

### The words are not code

Disassembling them in either image produces nonsense:

```
0x78C58C  retail f0fc3700  ->  ldrshteq pc, [r7], -r0
0x78E604  retail 70dc3700  ->  eorseq sp, r7, r0, ror ip
0x78E7E8  retail 00dc3700  ->  eorseq sp, r7, r0, lsl #24
0x795FF0  retail 78653700  ->  eorseq r6, r7, r8, ror r5
0x7960F8  retail a4623700  ->  eorseq r6, r7, r4, lsr #5
0x7982D8  retail 28413700  ->  eorseq r4, r7, r8, lsr #2
```

Conditional data-processing ops with nonsensical operand/shift combinations are what a
disassembler produces for **data read as code**.

### They are small integers

Reading each as a whole little-endian word gives values under `0x01000000`, and retail
and patched differ by a near-constant amount:

| site | retail word | patched word | delta |
|---|---|---|---|
| `0x78C58C` | `0x0037FCF0` | `0x003BCE98` | `+0x3D1A8` |
| `0x78E604` | `0x0037DC70` | `0x003BAE18` | `+0x3D1A8` |
| `0x78E7E8` | `0x0037DC00` | `0x003BADA8` | `+0x3D1A8` |
| `0x795FF0` | `0x00376578` | `0x003B3664` | `+0x3D0EC` |
| `0x7960F8` | `0x003762A4` | `0x003B3390` | `+0x3D0EC` |
| `0x7982D8` | `0x00374128` | `0x003B11E0` | `+0x3D0B8` |

A near-constant positive delta across six unrelated addresses is the signature of a
build whose internal layout shifted and whose absolute pointers were recomputed — not of
six pointers being individually retargeted at named tables.

> Correction to an earlier draft of this document: this is **not** a relink in the ELF
> sense. The retail and reference images have byte-identical program headers — same five
> segments, same file offsets, same sizes (`0x45C/0x9AE990`, `0x9AEDEC/0x210A53`,
> `0xBBF83F/0xBB274`, …). Nothing was relinked at the ELF level. Any shifting happened
> *inside* `.text`. We do not have a confirmed explanation for these six words.

### Neither side points at a table

The labels claim the patch relocates a table. It does not:

| | retail target | patched target |
|---|---|---|
| `body_table_redirect_a` | `0x37FCF0` → array of pointers (`0x8EAD88`, `0x8E3064`, …) | `0x3BCE98` → `0xE30D270A` = `movw r2, #0xD70A` |
| `height_table_redirect_a` | `0x376578` → code | `0x3B3664` → code |
| `draw_offset_redirect` | `0x374128` → code | `0x3B11E0` → code |

Every patched target lands in `.text` at executable instructions. And the data hooks
wrote float tables at `0xB493A8`–`0xB4942C`, which is **all zeros in retail and is not
referenced by anything** — no reader was ever redirected there.

So the two halves of the file contradicted each other: tables were written to a region
nothing pointed at, while the readers were pointed at code.

### Why rendering broke before the Hammer appeared

The two height sites (`0x795FF0`, `0x7960F8`) sit in the per-actor height and draw-offset
lookup path, which runs for **every actor drawn, every frame**. Feeding it code bytes as
if they were `f32` heights yields values like `-8.56e+22`, so actors are placed and
scaled absurdly. That is a global, immediate rendering fault — exactly as reported, and
independent of the Hammer.

### Fix

All six redirects removed. All 29 `data` hooks removed (they fed nothing). The originals
are preserved verbatim in `hooks_reference/`.

## Cause 2 — `pukupuku.cpp` hijacked retail profiles 530 and 539

`code/pukupuku.cpp` ended with two **file-scope** objects:

```cpp
const Profile pukupukuProfile(&Pukupuku::build, ProfileId::Pukupuku, "pukupuku", nullptr, 0);
const Profile pukupukuTogeProfile(&PukupukuToge::build, ProfileId::PukupukuToge,
                                  "pukupuku_toge", nullptr, 0);
```

`ProfileId::Pukupuku` and `ProfileId::PukupukuToge` are **retail ids (530, 539)**, not
custom ids. File-scope objects run their constructors when the subsdk loads.

The real `Profile` constructor at `0x60017F6C` ends with:

```asm
movw r3, #0x392          ; 0x392 = 914 = NUM PROFILES_ORIGINAL
cmp  r2, r3              ; r2 = id
movlo r1, r2             ; if id < 914, r1 = id
ldr  r2, [pc, #0x10]
add  r2, pc, r2          ; r2 = &profiles[]
str  r0, [r2, r1, lsl #2] ; profiles[id] = this      <-- UNCONDITIONAL
bx   lr
```

There is **no check that the id is a custom id**. `Profile::get` (`0x182A0`) reads the
same array:

```asm
movw r1, #0x392          ; 914
cmp  r0, r1
movhs r0, #0             ; id >= 914 -> NULL
ldr  r1, [pc, #0xc]
add  r1, pc, r1
ldr  r0, [r1, r0, lsl #2] ; profiles[id]
```

So simply loading our subsdk **replaced the game's own Pukupuku (530) and PukupukuToge
(539) profiles** with our reconstructions. Every Cheep Cheep and Spiny Cheep Cheep in
every level would then be built by our code, which sets `mpModel` from
`ModelWrapper::create("pukupuku","pukupuku")`, leaves `mpResource` null, and does not
reproduce retail behaviour.

That is a second, independent route to both misrendering and crashes on actor spawn.

### Fix

`pukupuku.cpp` moved from `code/` (compiled) to `findings/` (documentation only). It
remains valuable as a record of the field layout — the offsets marked `[V]` are still
verified — but it must not be compiled. If a real custom actor is ever wanted, give it an
id `>= 914` and use `PROFILE_RESOURCES` so it lands in the custom arrays.

This is now the rule: **never declare a file-scope `Profile` with a retail id.**

## What still ships

| file | hooks |
|---|---|
| `hammer_actor.hks` | 7 instr |
| `hammer_profile.hks` | 1 instr, 4 data |
| `hammer_projectile.hks` | 8 instr |
| `item_grant.hks` | 4 instr |
| `mode_tables.hks` | 1 instr (`mode_six_or_ten`) |

21 instruction hooks + 4 data hooks, versus 35 + 32 before. The IPS shrank from 755 bytes
/ 83 records / 332 patched bytes to 233 bytes / 25 records / 100 patched bytes, and
`subsdk0` from 29,841 bytes to 577 bytes (the patch is now essentially all IPS).

The four load-bearing Hammer bytes are still present and verified byte-exact:

```
0x465F40  movw r1, #0x3FB   fb 13 00 e3
0x46600C  movw r1, #0x3FB   fb 13 00 e3
0x45DDCC  mov r2, #10       0a 20 a0 e3
0x78E6A8  cmp r0, #10       0a 00 50 e3
```

`0x3FB` sets bit 9 (mode 10), which retail's `0x1FB` does not. That is what makes the
feature reachable at all.

## Honest status

* **Cause 1 is fixed and the evidence is strong.** The redirects provably pointed at code
  and provably fed nothing.
* **Cause 2 is fixed and the evidence is conclusive** about the mechanism — the
  constructor stores unconditionally. Whether it was *your* crash specifically, versus
  the redirects, cannot be separated without testing, because both were live at once.
* **The crash itself is not reproduced.** No test has been run since these fixes.
* **The `0xC61BE4` profile-cell hook is still unverified.** It swaps a pointer from a
  table starting at 476 to one starting at 759. Both are tight runs of consecutive ids,
  so the swap is like-for-like in *form*, but we have not established how the cell is
  indexed. If a caller indexes it by power-up mode, mode 10 reads index 10 → profile
  **769**, not 759. Worth checking first if a Hammer-specific fault remains.

### If problems persist

Bisect in this order — each step is independently removable:

1. Only `item_grant.hks` + `mode_six_or_ten` (the 5 gate hooks). Expect: Hammer becomes
   *reachable* but the player still looks like Fire Mario. If rendering is clean here,
   the redirects were the whole rendering story.
2. Add `hammer_actor.hks`. Expect: Hammer body geometry changes.
3. Add `hammer_projectile.hks`. Expect: throwing behaves differently.
4. Add `hammer_profile.hks` **last** — it holds the unverified cell.
