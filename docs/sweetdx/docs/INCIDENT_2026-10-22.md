# Incident: the first in-game test broke the game

**Date:** 2026-10-22
**Build tested:** `subsdk0` 577 bytes, IPS 233 bytes / 25 records / 100 patched bytes
**Result:** significant rendering corruption on level load, and a hard crash the moment the
Hammer power-up was touched.

This document records the diagnosis, including two wrong turns I took along the way. The
wrong turns matter more than the conclusion: each one was a plausible reading of the data
that further evidence overturned.

---

## Summary

Two independent faults were found. Neither is visible in a byte diff, and both passed
every automated check the repo had at the time.

| # | Fault | Effect |
|---|---|---|
| A | `pukupuku.cpp` was compiled, and its file-scope `Profile` objects used **retail** ids 530/539 | replaced the game's own Cheep Cheep profiles at load |
| B | `hammer_profile.hks` pointed the power-up profile cell at 759 instead of 476 | replaced the Fire Flower identity check rather than adding a Hammer slot |

Fault A is the strong candidate for the rendering corruption: it damages base-game content
before any Hammer is involved. Fault B is the candidate for the crash on pickup.

A third change — the six "mode table redirect" hooks — was wrongly blamed and wrongly
removed, then restored. See the correction section; that mistake is instructive.

---

## Fault A: a compiled `Profile` object overwrote the game's own profiles

### Mechanism

`Profile`'s constructor writes itself into a global table, unconditionally:

```asm
; _ZN7ProfileC2... @ 0x60017F6C
60017FA4  MOVW  R3, #0x392          ; 914, the table bound
60017FA8  CMP   R2, R3              ; R2 = the id argument
60017FAC  MOVCC R1, R2
60017FB0  LDR   R2, =(Profiles - 0x60017FBC)
60017FB4  ADD   R2, PC, R2
60017FB8  STR   R0, [R2, R1, LSL#2] ; Profiles[id] = this
60017FBC  BX    LR
```

There is no "already registered" guard. Constructing a `Profile` with an id that the game
already owns **replaces** that entry.

`pukupuku.cpp` declared file-scope `Profile` objects for the Deluxe Cheep Cheep family using
ids **530** and **539**. Those are the ids the retail game assigns to Pukupuku. Because the
objects are at file scope, merely loading `subsdk0` ran the constructors, so the game's own
profiles were replaced by ours before the first level loaded.

### Why this looked fine

Our replacements described the same actors. The bug is not that the data was wrong; it is
that there were now **two** definitions and ours won. Nothing in a byte-level comparison of
the patch against the reference image can see this, because the reference image contains
the same substitution by design — it is a full replacement build, not a patch.

### Fix

`pukupuku.cpp` moved to `sweetdx/findings/` and is no longer compiled. The offsets recorded
in it are still valid as reference; the file now carries a header explaining why it must not
be compiled. `sweetdx/code/` contains only `powerup_modes.cpp`.

**Rule this establishes:** a `code/` file that constructs engine-side objects has side
effects at load. Findings that merely *describe* an engine object belong in `findings/`.

## Fault B: the profile cell swap

### What the cell is

This took two corrections to get right, so the settled version first:

- `[0xC61BE4]` holds a **pointer**.
- Retail: `0x00AF3498`. Ours: `0x00AF3904`.
- The region `0xAF2D28 .. 0xAF3B60` is **one run of 911 consecutive integers, 0 … 910**
  (`find_mode_tables.py`, `check_759_literal.py`). Element *n* holds the value *n*.
- So retail's pointer reads **476**, and ours reads **759**. There is no table of tables.
- 37 of 40 access sites do a plain `LDR Rn, [Rm]` at offset 0 — **no index register**, no
  stride. The three apparent "offset 533" sites were `LDRB` on unrelated fields.

The readers compare that value against the actor's profile id:

```c
// sub_6000A2E8
v8 = MEMORY[0xAF3498];                       // = 476
result = Actor::getProfileId(*v4);
v10 = (result == v8);                        // "is this actor the Fire Flower?"
```

So the cell answers **"which profile counts as the fire-power actor"**. It is a single
identity, not a mode-indexed table.

### Why the hook is unsafe

The hook rewrites the pointer so the cell yields 759 instead of 476. That does not *add* a
Hammer slot; it **replaces the Fire Flower identity everywhere**. Consequences:

- Fire Mario stops being recognised by code that looks for profile 476, including the
  projectile path.
- That same code is simultaneously told to treat profile 759 as the fire actor.

Mode 10 is already enabled by `item_grant.hks` (`0x1FB → 0x3FB`, adding bit 9) plus
`0x45DDCC` (`mov r2,#2 → #0xa`). The cell swap contributes nothing to reachability, so its
only effect is the identity substitution.

### Corrections to earlier claims about this cell

- **Wrong:** "the cell is a mode-indexed table base." It is a single id.
- **Wrong:** "`Profile::get(759)` returns NULL, so the caller faults." 759 is inside
  0 … 910, and there are exactly **911** `Profile` constructor call sites, so 759 is a
  registered profile. `Profile::get` does bound-check (`MOVW R1,#0x392; CMP; MOVCS R0,#0`),
  but 759 is in range and resolves to a real object.
- **Wrong:** "the patched pointers aim live lookups at executable code." See below.

### Fix

`hammer_profile.hks` moved to `sweetdx/experimental/` and is **not loaded** by the default
build. `grant_hammer_mode` (0x45DDCC) and the three `ActorInfo` writes moved with it, since
they are the other unproven hooks.

## Correction: the six "mode table redirect" hooks were NOT the bug

I removed these six hooks, and the associated 29 data hooks, believing they pointed live
lookups at executable code. **That was wrong, and removing them was wrong.** They are
restored and verified.

### The mistake

I read the six literal-pool words as **absolute addresses**:

```
retail 0x0037FCF0  "points at" ... something
ours   0x003BCE98  "points at" ... ARM code (0xE30D270A = movw r2,#0xD70A)
```

They are not addresses. They are **PC-relative offsets**, used by the standard ARM idiom:

```asm
LDR Rn, =(table - pc)
LDR Rn, [PC, Rn]          ; Rn = table address
```

so `stored + pc = table`. Applying the relation to retail:

```
0x0037FCF0 + 0x0078C540 = 0x00B0C230   <- the real body table
```

and to our value:

```
0x003BCE98 + 0x0078C540 = 0x00B493D8   <- the relocated body table
```

Both decode exactly (`decode_reference_tables.py`, `solve_literals.py`). All six resolve to
sane relocated tables, and those tables match the reference build **byte for byte**.

### Why the relocation is genuinely needed

Three tables are indexed by power-up mode and have exactly **ten** entries (modes 0–9):

| table | address | values | mode 10 would read |
|---|---|---|---|
| body | `0xB0C230` | 1,0,0,1,2,3,0,4,4,5 | **165** — not a valid body type |
| height | `0xB0C2BC` | 16,31,31,6,31,31,31,31,31,31 | 0.0 |
| balloon offset | `0xB0C34C` | 0,−4,−4,4,−5,−2,−4,−4,−4,0 | 0.0 |

A fourth, reached through a variable-index getter with **no bounds check** at `0x60796A60`:

```asm
60796A60  LDR R0, =(dword_60B0C300 - 0x60796A6C)
60796A64  ADD R0, PC, R0
60796A68  LDR R0, [R0, R1, LSL#2]      ; R1 = index, unchecked
60796A6C  BX  LR
```

Its table starts at `0xB0C300`; `0xB0C328` is element **[10]**.

Extending in place is impossible — the words immediately after each table belong to
something else (`check_table_room.py`). So the reference build relocated copies and
repointed the readers, and we do the same, at the same RVAs:

| table | relocated to | 11 entries, mode 10 last |
|---|---|---|
| height | `0xB493A8` | 16,31,31,6,31,31,31,31,31,31,**31** |
| body | `0xB493D8` | 1,0,0,1,2,3,0,4,4,5,**0** |
| balloon | `0xB49404` | 0,−4,−4,4,−5,−2,−4,−4,−4,0,**−4** |
| tall actor | `0xB0C328` (in place) | **2** |

Those addresses are exactly where the "data hooks" were writing all along. The data was
right; my reading of the *literals* was wrong.

### A second, smaller mistake in the same area

Restoring the hooks, I hand-wrote the payload hex and got four bytes wrong in the balloon
table, writing 40 bytes into a 36-byte span. Caught by comparing against the reference
build. All payloads are now **generated** from `convertedmain.hammer_b.elf`
(`gen_table_payloads.py`) rather than transcribed.

The reader words are also now tagged `data` with exact DCD bytes instead of `instr` with
mangled text. I checked that the tested build's `instr` text did assemble to the right
values (`test_tested_build_bytes2.py`, 6/6 correct) — so the tested build's bytes were
fine. `data` is still the safer tag: an `instr` hook on a data word relies on the
assembler reproducing the exact bytes, which is a needless round trip.

## What that leaves

Fault A explains world-wide corruption at level load, which matches the first symptom and
involves no Hammer at all. That is the strongest lead, and it is fixed.

Fault B is a real design error and is quarantined. Whether it was *the* crash is not proven:
the tested build also contained `grant_hammer_mode` and the three `ActorInfo` writes, which
remain unproven and are quarantined with it.

The current default build therefore ships:

- `item_grant.hks` — the gate that makes mode 10 reachable
- `mode_tables.hks` — the 11-entry tables and six reader repoints
- `hammer_actor.hks`, `hammer_projectile.hks`
- `powerup_modes.cpp`

But **not** `grant_hammer_mode`. So the default build does not currently enable the Hammer
at all: it widens the gate and prepares the tables, without a way to enter mode 10. That is
deliberate — it lets the rendering fix be tested in isolation.

---

## Bisection order for the next test

Run these in order and stop at the first failure. Each step is one rebuild.

1. **Base only** — the default build as it stands, no `experimental/`. Expect a clean level
   with no rendering corruption. This tests Fault A's fix.
2. **+ `grant_hammer_mode`** (copy `experimental/hammer_profile_experimental.hks` and delete
   every hook in it except `grant_hammer_mode`). Expect the Hammer to be obtainable and to
   apply. If it crashes here, the crash is in mode 10 itself, not in the profile cell.
3. **+ the three `ActorInfo` writes.** These are the most likely to affect unrelated actors.
4. **+ `hammer_profile_cell` last.** Expect Fire Mario to regress; if the game now crashes
   on Fire Flower pickup instead of Hammer, that confirms the identity-substitution
   mechanism.

## Checks that would have caught these

| Fault | Check | Now implemented |
|---|---|---|
| A | refuse to compile file-scope engine singletons | `findings/` split + README rule |
| A | flag any `.cpp` whose objects register into engine tables | manual review note |
| B | prove a patched field is *added*, not *substituted* | `check_759_literal.py`, this doc |
| both | never infer correctness from diff fidelity | README rewritten |

The last row is the important one. Every hook in that build reproduced the reference image
faithfully, and a validator confirmed it — 59 of 59 words, zero mismatches. It still broke
the game. **Diff fidelity says the bytes are the same; it says nothing about whether those
were the right bytes to change in a patched retail image rather than a full replacement
build.** That is the lesson worth keeping.
