### The real one

- `0x00008A78` / `sead__SafeStringBase__assureTerminationImpl_const`: class and member agree exactly; the only disagreement is a cv-qualifier — our name says `_const`, the mangling `_ZN4sead14SafeStringBaseIcE22assureTerminationImpl_Ev` carries no `K`. Not reconciled: one of the two names is wrong about the signature, and these files cannot say which.

This is *not* a claim that the two names denote different functions. Both name `sead::SafeStringBase<char>::assureTerminationImpl_` at `0x00008A78`; they disagree only on whether it is `const`. It is marked `real` because a qualifier mismatch is a difference in what is being asserted, which notation reconciliation is not entitled to paper over.

It cannot be settled from code. On the 32-bit ARM ABI a member function's `const` qualifier does not appear in the calling convention, the symbol, or any instruction — a `const` and a non-`const` version of the same function compile to identical machine code. Only the class declaration settles it, and that is not an input here. What the repo's own data says: of the 15 flattened `_const` names in `symbols.csv` that join to a codedx entry, 14 match a `K` in codedx's mangling and 1 (this one) does not — so the convention is applied correctly 93% of the time and this is the single exception, which makes an over-applied suffix the likelier reading without proving it.

## 5. What is still open

- **`LOADER_STATUS.md` lines 97-98 still say 117.** This report measures 45. The doc is left untouched (this task was scoped to new files only), so the two disagree until someone edits it.
- **The 1 `real` verdict is unsettled, and no amount of disassembly will settle it.** `0x00008A78` is the same function under both names; the disagreement is the `const` qualifier. `const` is not encoded in the 32-bit ARM calling convention, so both readings compile to identical code and the binary cannot arbitrate. The lean is that our `_const` is over-applied — 14 of the 15 flattened `_const` names that join a codedx entry match a `K` in the mangling, and this is the one that does not — but a lean is not a measurement, so it stays `real`.
- **A cosmetic verdict is not a signature check.** A cosmetic verdict means the *name pair* is reconcilable, not that our signature is right: parameter lists were deliberately dropped from the comparison, so an arity or type error would not show up here. The `_const` qualifier test in §4 is the only qualifier check performed, and it compares two names, not a name against the code. Note that our repo uses `_const` only on flattened names (172 of them) and never on a mangled one, so the check can only ever fire on the flattened side.
- **`MISSING` is 0 by construction here, not by proof.** Both inputs cover the same image, and our export lists only named symbols; a codedx address our IDB holds as `sub_` would be absent from `symbols.csv` and would read as `MISSING`. It reads 0, so on this export that does not occur — but `CODEDX_REFERENCE` §1's older "MISSING (IDB has sub_): 26" cannot be re-checked from these files and is not confirmed or refuted here.
- **910 rows in `symbols.csv` are labelled `kind=data` but sit in a code section with `size=0`** (e.g. `0x000008DC` `_ZN10StageActor11isOffScreenEv`; 746 of them are `jpt_` jump tables). They are code by section, and are classified as code here; the `kind` column is what is wrong. Left untouched.
- **The 5 vtable-slot placeholders in §4 are the actual open work.** codedx names them (`Enemy::freeze`, `Enemy::beginState_Ice`, ...); we have `vfD0`/`vf264`. Those are real identifications waiting to be adopted, and they are a different problem from notation.
- **Data symbols are not reconciled in this report.** 25 codedx entries name data (`.bss`/`.data`/`.rodata`/`.got`); they agree or disagree by plain identifier and are counted in the MATCH/ALIAS buckets, but no layout or size claim was checked.
- **codedx's D0/D2 destructor pairs are collapsed.** codedx gives both `Actor::~Actor()` at `0x00002D98` and `0x00002E5C`; our names separate them by RVA suffix. Nothing is lost, but a name-for-name swap would be.
